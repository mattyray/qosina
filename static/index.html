Architecture & Design Reference

What I built, why I built it that way, and what would change in production at Qosina.

1 Stack at a Glance

LangGraph ReAct Agents
  • Reason → Act → Observe → repeat — agent decides which tool to call, reads the result, decides next step
  • Model-agnostic — same agent code regardless of which LLM is behind it
OpenRouter for LLM Resilience
  • Claude Sonnet 4 primary, GPT-4o and Gemini 2.5 Flash as failover
  • Anthropic goes down? — agent keeps working, different model, same code
  • Live demo — switch models in the header dropdown right now
Claude Vision (No OCR Product)
  • No Form Recognizer, no Tesseract, no Document Intelligence
  • How it works — PyMuPDF renders PDF pages to PNG, sent directly to Claude Vision
  • Claude reads the image natively — handles handwriting, messy scans, any format
SQLite with OData-Shaped Responses
  • 17 tables — all return D365 F&O OData JSON format
  • Same field names, same JSON shape, same @odata.context headers
  • Production swap — URL + auth change, not a rewrite
Application Infrastructure
  • FastAPI (Python 3.12) + vanilla JS with Tailwind CDN
  • SSE for real-time streaming responses
  • Docker on Railway — auto-deploy from GitHub main
  • ~7,800 lines of code, 64 unit tests across 4 test files

2 Human in the Loop

  • Zero write tools to the system of record — reads everything, can't modify anything
  • Only write tool is create_approval — adds a recommendation to a queue, that's it
  • Enforced in code, not policy — there's literally no tool for the agent to call, even if someone tried to bypass it
  • Review panel — side-by-side: original document, AI summary, editable fields with confidence colors
Goal isn't to replace anyone — improve workflow so the team has time for higher-value work (growth, analysis, vendor relationships). AI handles repetitive extraction and matching; humans make the decisions.

3 The Three Use Cases

  • Each UC — business problem, what I built, production recommendation
  • Different recommendation per UC — not pushing one stack for everything
  • Need your guidance — my recs are research-based, not hands-on with Qosina's systems
  • All assume D365 F&O as system of record, Celigo for existing integrations (Section 8)
UC1

Sales Order Entry

CX Department
The business problem
  • POs arrive in every format — clean PDFs, scans, handwritten, email body text
  • Today — someone reads each one, manually keys into D365 as a sales order
  • Pain — slow, doesn't scale, typing errors caught downstream when something ships wrong
What I built
  • Drop a PO in any format — PDF, image, paste text
  • Agent extracts — customer, contact, PO#, line items, ship-to, delivery date, terms
  • Five tools — match_customer → match_products (fuzzy vs catalog) → validate_pricing → check_inventory → create_approval
  • Confidence scores — red/yellow/green borders show reviewer exactly what needs checking
My recommendation: Hybrid (n8n + Custom Python)
n8n — Trigger Side
  • Watch inbox for PO emails
  • Extract attachments
  • Route to Python webhook
  • Visual flow, business analysts can maintain it
Custom Python — AI
  • Claude vision parses any format
  • Fuzzy match vs 5K SKUs
  • Confidence scoring
  • Full pytest coverage
* Built in this demo
Power Platform
  • AI Builder is for structured forms
  • Can't fuzzy match 5K SKUs
  • Can't use Claude natively
  • Why hybrid — n8n handles email plumbing (inbox, attachments, routing), Python handles AI reasoning
  • n8n piece is commodity work — visual flow, easier for team to maintain than code
  • AI piece needs Claude — fuzzy matching against 5,000 SKUs, confidence scoring
UC2

AP Processing

Finance Department
The business problem
  • Finance team called this "waste of human effort" in the brief
  • Three sub-jobs — three-way matching (pay vendors), cash application (allocate payments), collections (chase overdue)
  • Full of edge cases — penny rounding, partial payments, mystery checks, price increases
  • Today — all manual, long tail of edge cases eats the team's time
What I built
  • Three-way matching — drop vendor invoice or click "Match All" → three_way_match compares line-by-line → tolerance thresholds → fast-track or flag
  • Cash application — drop remittance or click "Cash Application" → match_payment proposes invoice allocation → handles partial pays and deductions
  • Collections — click "Collections Priority" → score_collections ranks by amount + age + payment trend + tier
My recommendation: Power Platform + Custom Python
n8n
  • Could work, no advantage
  • D365 F&O needs HTTP node
  • No native D365 F&O connector
Power Platform — Core
  • Native D365 F&O connectors
  • Built-in Approvals via Teams
  • Audit trail for free
  • Finance already uses it
* The right call here
Custom Python — Intelligence
  • Cash app reasoning
  • Collections risk scoring
  • Claude judgment calls
* Called from Power Automate
  • Explicitly NOT recommending my own stack as the core here
  • Microsoft built the boring 90% — D365 connectors, Teams approvals, audit trail. You're already paying for it
  • Python is just the 10% — AI judgment calls on cash app and collections scoring
Why not Copilot Studio?
  • Copilot Studio — strong for chatbot-style assistants over knowledge bases, not multi-tool ReAct agent loops
  • AI Builder — designed for templated forms, not the variable formats the brief called out
  • Bottom line — intelligence layer stays in Python even when orchestration is Power Platform
UC3

Product Data Entry

Product Development
The business problem
  • New SKU sourced — supplier sends spec sheets, CoAs, catalog pages, technical drawings
  • Today — someone manually extracts 30+ fields per SKU, types into D365 item master
  • 8,000+ existing SKUs, new ones added regularly
  • "Constitutional framework" — the brief called this out: non-negotiable rules for translating supplier terminology into Qosina's standards
What I built
  • Drop a spec sheet — Claude reads it directly
  • Loads constitutional rules via get_naming_conventions from a database table
  • Normalizes every field — "PC plastic" → "Polycarbonate (PC)", inches → mm, "valve" + luer → "Stopcock"
  • Consistency check — find_similar_products compares against existing catalog, validate_consistency checks rules
  • Approval grouped by section — Basic Info, Dimensions, Connections, Compliance, Commercial
The constitutional framework is the interesting part
  • Rules live in a database table, not in code — adding a rule is an INSERT, not a deployment
  • Product Dev team maintains their own rules through an admin UI, no developer needed
  • Belt and suspenders — enforced in the agent's prompt AND in validation code
Downstream connection: Landed cost estimation
  • Fields the agent extracts — country of origin, tariff code, MOQ, unit price, weight
  • Direct inputs to landed cost — product cost + freight + duties + insurance + handling
  • Agent doesn't calculate landed cost — that's StockIQ / D365 costing
  • Agent ensures clean inputs — garbage in, garbage out is the failure mode
My recommendation: Full Custom Python
n8n
  • AI Agent node available
  • Constitutional rules need code precision
  • Hard to test/validate
Power Platform
  • AI Builder not strong enough
  • Can't enforce naming rules precisely
  • Not Claude-native
Custom Python — Full
  • Constitutional rules in DB + prompt
  • Validation in code (belt + suspenders)
  • Consistency check vs catalog
  • Full Claude reasoning
* Built in this demo
  • Constitutional framework needs precision — can't have no-code subtly mistranslating "PC plastic" as "Polycarbonate (Plastic)"
  • Rules must be testable and enforceable — low-code tools can't give you that
  • Lower volume — new product entries, not hundreds of POs/day, so orchestration tax isn't worth it

  • Each renders differently in the review panel
  • Production — each routes to a different D365 write-back (sales orders, payments, item master, CE activities)
  • Specifics depend on how Qosina's D365 and Celigo are configured
Type Use Case What it answers

INVOICE MATCH UC2 Should we pay this vendor invoice?
PAYMENT APPLICATION UC2 Which invoice does this customer payment pay off?

6 Accounts Payable — The Three Sub-Jobs

  • Biggest impact — the brief called it "waste of human effort"
  • Three sub-jobs — AI handles analysis, humans always make the final call
Direction Sub-job The question being answered
Money OUT Three-way match "Should we pay this vendor's bill?"
Money IN Cash application "Which open invoice does this customer payment pay off?"
Money LATE Collections "Which overdue customer should we call first?"
Three-way matching (money out)
  • Three docs must agree — PO (what we ordered) vs receipt (what arrived) vs invoice (what vendor charged)
  • All agree? Bill gets paid. Don't agree? Investigate before money moves
  • Without it — pay for parts that never arrived, wrong prices, duplicate payments
  • Agent output — green (perfect match), yellow (penny variance, write-off), red (real discrepancy, hold)
Cash application (money in)
  • Customer sends payment — Finance figures out which open invoice(s) it pays off
  • Hardest of the three — checks with no remittance, one check covering three invoices, wrong amounts from deductions/discounts
  • Until cash is applied — customer shows as overdue even though they paid, you call asking for money they already sent
  • Agent proposes allocation — reviewer adjusts before applying
Collections prioritization (money late)
  • 200 overdue accounts on any given day — can't call them all, which first?
  • Smart scoring — amount owed + days overdue + payment history + account size + last contact
  • DSO (Days Sales Outstanding) — top metric finance teams are measured on
  • Cutting DSO from 65 to 50 days — tens of thousands in cash flow improvement

7 OpenRouter

  • Claude Sonnet 4 (primary) — best reasoning for fuzzy matching, constitutional framework, complex extraction
  • GPT-4o (failover) — auto-routes if Anthropic is down or rate-limited (~25ms overhead)
  • Gemini 2.5 Flash (failover) — different provider, different region, completely separate infrastructure
  • Why it matters — enterprise systems can't go down because an LLM provider is having a bad day
  • One API key, one bill, one dashboard — provider data policies enforced (no training on Qosina data)
  • If OpenRouter itself breaks — flip a feature flag, call Claude or OpenAI directly
Live demo — will switch between Claude, GPT-4o, and Gemini mid-demo to show the system is model-agnostic.

9 Observability & Audit

  • Three things matter for medical device compliance — regulated industry, this isn't optional
User accounts in production
  • Don't roll my own — Qosina is on Azure, everyone already has Entra ID (Azure AD)
  • OAuth flow — login through Microsoft, JWT comes back, FastAPI middleware validates
  • Authorization via AD groups — "AP_Approver", "CX_Manager", "Product_Dev_Lead"
  • IT already manages groups — I'm just consuming that. Don't rebuild what you own
Troubleshooting FastAPI in production
  • Structured JSON logging → Azure Log Analytics
  • Sentry / Application Insights — error tracking with full stack traces
  • Health endpoint at /health for liveness probes
  • Application Insights APM — latency, error rates, dependency tracing (already on Azure)
  • LangSmith for AI traces — most important one, see below
Auditing the AI agent — the FDA story
  • Auditor pulls approval #5234 six months later — needs original PO, full conversation, every tool call, AI reasoning, who approved, final D365 order
  1. Persist conversations — conversations + conversation_messages tables
  2. FK approvals back to the conversation that produced them
  3. Azure Blob Storage for source documents — 7+ year retention (FDA medical device)
  4. Append-only audit log — tamper-evident
  5. LangSmith — every LLM call, every tool input/output, searchable, step-by-step replay

Honest framing: integration work, not algorithm work. Architecture supports it. Phase 1 alongside UC1.

10 Phased Rollout Plan

  • Each phase compounds — Phase 1 builds foundation that Phase 2 and 3 inherit
  • Sequence — simplest first, highest dollar impact second, most reasoning-heavy last
PHASE 1

UC1 — Sales Order Entry

Foundation phase
Why this first:
  • Simplest — one approval type, one team (CX), standard product orders only
  • Foundation phase — stand up all shared infrastructure Phase 2 and 3 inherit
  • Safe fallback — reviewer rejects approval, order processed manually like today
What gets built — UC1 flow:
  • UC1 productionized — D365 F&O/CE via OData, n8n trigger + Python AI service
What gets built — foundation (Phase 2 and 3 inherit all of this):
  • Entra ID OAuth — login through Microsoft, JWT validation in FastAPI middleware
  • AD groups for authorization — "CX_Manager", "AP_Approver", "Product_Dev_Lead" — IT already manages these
  • Application Insights — latency, error rates, dependency tracing (already on Azure)
  • LangSmith — AI agent tracing, every LLM call and tool call, step-by-step replay
  • Persisted conversations — SQL tables with FK to approvals, audit trail
  • Azure Blob Storage — source documents with 7+ year retention (FDA medical device)
  • Sentry — error tracking with full stack traces
  • Health checks + alerting — /health endpoint for liveness probes
  • Celigo flow mapping — understand existing integrations, don't rebuild what's wired
UC1 is the vehicle — the foundation is the real deliverable
Discovery first (shadow the CX team):
  • Can I see 50+ real POs from the top 10 customers? What's the actual format distribution?
  • Where does real-time inventory truth live — D365 F&O or PowerHouse WMS?
  • How are trade agreements (customer-specific pricing) structured in D365?
  • What's the new customer onboarding process when someone orders for the first time?
  • How is the product catalog structured in F&O — standard fields, extended attributes, or dimension groups?
  • What existing Celigo flows touch these processes? Don't rebuild what's already wired
  • Does StockIQ already handle low-stock alerts and reorder recommendations?
  • Can I shadow each team for a week? CX processing POs, Finance matching invoices, Product Dev entering specs
PHASE 2

UC2 — AP Processing

Highest dollar impact
Why this second:
  • "Waste of human effort" — where Qosina is losing the most money
  • Foundation from Phase 1 already in place
Sub-phased delivery:
  • Three-way matching first — most deterministic, easiest to validate
  • Cash application second — builds on same approval pattern
  • Collections third — lowest write risk, just produces a ranked list
Architecture shift:
  • UC1 was n8n + Python → UC2 is Power Platform + Python
  • Power Automate handles D365 reads/writes + Teams approval routing
  • Same Python service from Phase 1 called via HTTP — new tools, same service
Discovery first (shadow the Finance team):
  • How do vendor invoices get into D365 today? Manual entry, EDI, Celigo flow from email?
  • What tolerance thresholds does Finance actually use? Are there vendor-specific rules?
  • What percentage of customer payments arrive with remittance advice vs without?
  • How does the team prioritize collections today? What's DSO and what's the target?
  • Which customers are notorious for short-pays or unauthorized deductions?
  • Does anyone use D365 CE for collection activities, or is it tracked in spreadsheets?
  • Approval authority by dollar amount — set up AD groups correctly
  • Map existing Celigo flows — don't rebuild what's already working
PHASE 3

UC3 — Product Data Entry

Most reasoning-heavy
Why this last:
  • Lowest volume — new SKUs periodically, not hundreds per day
  • Most reasoning-intensive — want foundation rock-solid first
  • Most pre-work — constitutional framework is tribal knowledge nobody has codified
What gets built:
  • UC3 productionized as full custom Python — same service, new agent + tools
  • Admin UI for Product Dev team to edit constitutional rules themselves
  • Rules in database — no developer needed for new rules
Discovery first (longest — shadow Product Dev):
  • What are Qosina's actual naming conventions? (Demo has 16 placeholders — real ones are tribal knowledge, weeks to codify)
  • How are 30+ product fields structured in D365 F&O? Standard item master or custom extensions?
  • What does landed cost calculation need from product data — D365 costing or StockIQ?
  • Do technical drawings need vision AI, or are they handled differently?
  • Audit 30-50 existing entries → extract implicit naming conventions → build framework table
The compounding story:
  • Phase 1 — foundation (auth, observability, audit, deployment) with simplest UC
  • Phase 2 — highest-value AI work on that foundation
  • Phase 3 — most reasoning-heavy work on a mature platform
  • End state — three production workflows, one shared platform, pattern extends to future UCs
